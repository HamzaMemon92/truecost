# TrueCost Architectural Decisions

## 1. Deterministic Grocery Search Engine (Phase 2)
**Context:** We need a way to filter, match, and return grocery items predictably without relying exclusively on expensive and non-deterministic LLM queries, especially during standard search or catalog browsing.

**Decision:** We implemented a Deterministic Search Engine with the following components:
- **Normalization:** Standardizes weights and volumes to continuous scales (kg, L) to allow math-based matching and comparison.
- **Intent Parser:** A regex-and-heuristic-based parser that maps natural language queries (e.g. "amul milk under 60") into structured `SearchIntent` representations.
- **Canonical Catalog:** A centralized mocked catalog of `CanonicalProduct` objects representing real items.
- **Matching Algorithm:** Uses hard constraints (category, max price) and strong signals (brand, exact quantity, variant) to score items against the intent.

**Consequences:**
- Tests can be predictably asserted.
- System is much faster and cheaper.
- Strict reliance on dictionary synonyms in heuristics means some NLP fuzzy matches may fail unless explicitly added, suggesting a future hybrid model where deterministic search is augmented by a lightweight embedding or LLM pass for "no-results" fallbacks.

## 2. Backward Compatibility for Mock Providers
**Context:** The existing Basket Engine pipeline depended on `CanonicalGroceryItem` schemas being output by `MockGoldenGroceryProvider`, `MockFastGroceryProvider`, and `MockCheapGroceryProvider`. We needed to upgrade to the deterministic engine without breaking those downstream consumers.

**Decision:** The mock providers were refactored to parse intents, search the `CanonicalCatalog`, and map the winning `CanonicalProduct` entities back into the backward-compatible `CanonicalGroceryItem` dictionary shapes. The original price modifiers (1.3x and 0.8x) were preserved on the output level.

**Consequences:**
- The new search architecture is safely isolated behind the Provider interface.
- Downstream LangGraph nodes continue to function seamlessly without requiring schema rewrites.

## 3. Location, Availability, and Effective Pricing (Phase 2B)
**Context:** Products shouldn't be ranked purely by base price without factoring in location availability, exact delivery fees, platform fees, and discounts.

**Decision:** 
- A structured `Location` model was injected into the workflow. The mock providers intercept this location to deterministically simulate local stock-outs and regional unavailability.
- We created a centralized `PricingEngine` and `RankingService` that separates raw JSON prices from "Effective Cost". The effective cost explicitly breaks down discounts, platform fees, and delivery fees.
- Ranking logic (CHEAPEST, FASTEST, BEST_VALUE) applies strict mathematical rules but uses Availability as a hard gating constraint so that a cheap but out-of-stock item can never win.

**Consequences:**
- The UI will be able to display an explainable result (e.g. "Blinkit wins because 10min ETA + No delivery fee") using the structured explanation payload generated by the RankingService.

## 4. Product Image Integrity & Structural Fallbacks (Phase 4A)
**Context:** The mock catalog used random placeholder images (like unsplash), making it possible to show the wrong variant's packaging for a product (e.g. Amul 500ml packaging for a 1L product request).
**Decision:** We embedded explicit image metadata properties (`image_confidence`, `image_verified`) into `CanonicalProduct` and the `RetailerOffer` chain. We removed untrusted Unsplash URLs in favor of `FALLBACK` confidence flags. A unified resolver (`resolveProductImage`) guarantees the highest confidence image is selected deterministically across search, product cards, and the basket.
**Consequences:** TrueCost will never silently pair an untrusted or generic image with a specific product identity, preserving structural accuracy over visual completeness.

## 5. Retailer Exact SKU Deep-Linking (Phase 4B)
**Context:** When a user selects a winning retailer offer, we must hand off checkout directly to that precise product or cart. We cannot redirect them to a generic homepage.
**Decision:** We injected `deep_link_type` and `deep_link_url` straight into `CanonicalGroceryItem` and `FulfillmentGroup` schemas. The mock providers dynamically construct deterministic checkout URLs using the validated `canonical_product_id`. The UI enforces exactly these URLs for actions (e.g., "Get Deal" and "Open Blinkit"), keeping the identity chain unbreakable.
**Consequences:** Safe and explicit retailer destination mapping. Users are shielded from link leakage between competing retailers, protecting TrueCost's core promise of exact SKU mapping.

`EffectivePriceResult` applies `min(price, discount)` enforcing non-negative totals. Subtotals are strictly constrained to positive values to avoid absurd UI behavior when coupons exceed order thresholds. Python `round(val, 2)` prevents float precision errors.

### 10. Live Data Ingestion Hierarchy (Phase 7)
TrueCost fundamentally rejects unauthorized/brittle scraping. Integration must follow a hierarchy:
1. Authorized Retailer API / Partner Feed
2. ONDC Buyer Node
3. Verified Canonical Catalog (GS1)
Mock data must remain transparently mocked and never silently promoted to live status.

### 11. SKU Matching & Identity Strategy
Embeddings are insufficient for product identity. TrueCost requires strong deterministic keys: `GTIN/EAN/UPC`. If missing, fallback identity is derived via strict string normalization of `Brand + Title + Variant + Quantity`. Uncertain matches force the creation of new `CanonicalProduct` entities rather than risking false merges.

### 12. Verified Image Acquisition
Live retailer images are explicitly mistrusted. Retailer images are capped at `KNOWN_SOURCE` and will never automatically override an administratively `TRUSTED` image. AI-generated packaging or random web searches are completely forbidden. Primary image targets are trusted product databases or authorized feeds.

**Consequences:** TrueCost no longer hallucinates missing inventory and truthfully declares when simulating data, positioning the architecture to handle verified live retailers.
